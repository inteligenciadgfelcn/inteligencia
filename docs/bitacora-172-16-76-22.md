# Bitácora — servidor de prueba `172.16.76.22` (30-31/08/2026)

Registro completo de comandos ejecutados contra `172.16.76.22` durante la prueba de reproducibilidad de `deploy/`. Cada comando corrió vía SSH no interactivo (`ssh -p 50022 adminst@172.16.76.22 '<comando>'`), por eso no aparece en el `history` de una sesión interactiva del servidor — `bash` solo escribe a `.bash_history` en sesiones de login interactivas, no en comandos de un solo disparo ejecutados remotamente. Este documento es el registro real, más completo que `history`.

Ver también [07-servidor-nuevo-desde-cero.md](./07-servidor-nuevo-desde-cero.md) para la guía general (de la que este documento es una ejecución real), y los commits de la rama `fase1/reorganizacion-deploy` (`b0f814e3`..`2603cb99`) para los cambios de código/documentación que salieron de esta prueba.

## Fase 1 — Sistema base

```bash
sudo apt update && sudo DEBIAN_FRONTEND=noninteractive apt upgrade -y

sudo apt install -y ufw
sudo ufw --force reset
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 50022/tcp comment 'SSH (puerto no estandar)'
sudo ufw allow 80/tcp comment 'HTTP'
sudo ufw allow 443/tcp comment 'HTTPS'
sudo ufw --force enable

sudo apt install -y fail2ban
# /etc/fail2ban/jail.local con ignoreip ampliado a la IP de gestión real
sudo systemctl enable fail2ban
sudo systemctl restart fail2ban
# Incidente real: este restart baneó la IP de gestión por 2 intentos de login
# root fallidos minutos antes (backlog scan del backend systemd) — recuperado
# con `sudo fail2ban-client unban --all` desde consola física.

sudo tee /etc/ssh/sshd_config.d/99-hardening.conf > /dev/null <<'EOF'
PermitRootLogin no
PubkeyAuthentication yes
MaxAuthTries 3
X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
LoginGraceTime 60
EOF
sudo sshd -t && sudo systemctl reload ssh

sudo systemctl set-default multi-user.target   # graphical.target venía por defecto, sin GUI instalada
```

## Fase 4 — nginx (adaptado para IP sin dominio)

```bash
# Certificado autofirmado dentro del volumen certbot_certs (sin dominio no hay
# Let's Encrypt real posible):
docker run --rm --entrypoint sh -v development_certbot_certs:/etc/letsencrypt alpine/openssl -c "
  mkdir -p /etc/letsencrypt/live/172.16.76.22 &&
  openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
    -keyout /etc/letsencrypt/live/172.16.76.22/privkey.pem \
    -out /etc/letsencrypt/live/172.16.76.22/fullchain.pem \
    -subj '/CN=172.16.76.22' -addext 'subjectAltName=IP:172.16.76.22'

cd deploy/tools/nginx/conf.d
```

## Incidentes y correcciones post-verificación (31/08/2026)

- **Bug real de `<DOMINIO>` literal en los 3 `docker-compose.yml`**: el `environment:` de `base-frontend` tenía el placeholder sin reemplazar, y `environment:` pisa `env_file:` — el login fallaba en el navegador contra `https://<DOMINIO>/auth/api/auth`. Corregido a `${DOMINIO:?falta DOMINIO}` en los 3 compose (commit `2603cb99`).
- **Bug real de dato corrupto en seed**: `database/seeds/1786700000000-casbin-roles-f1.ts` tiene una política con `v1='user-profile.jpeg'` (rol `SEGUIMIENTO_CASOS`) — no es una ruta válida. El componente `ModulesByRole.tsx` del dashboard hace `objeto.split('/')[2].toUpperCase()`, y como ese valor no tiene `/`, revienta con `Cannot read properties of undefined` para **cualquier** admin que entre a `/admin/home` una vez que ese seed corrió. Mitigado en el frontend (omitir políticas con ruta malformada en vez de romper el gráfico completo) — **pendiente corregir el valor real de esa política en el seed**, requiere confirmar cuál era la ruta correcta.
